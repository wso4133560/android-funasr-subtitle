# Android CPU 性能验证（2026-09-11）

本次修复使当前手机的离线解码耗时显著下降，Bilibili 播放时也能连续输出字幕。
但长句仍有数秒等待，尚未证明声音到字幕显示的 P95 小于 2 秒，也未完成 30 分钟稳定性验收。

## 根因与修改

1. 原先 Gradle 的 `cppFlags += "-O3"` 只作用于 C++。实际编译数据库显示，
   GGML 的 6 个 C 源文件（包括量化点积与 CPU 内核）仍使用 Debug 的 `-O0`。
   现在在添加 GGML 子目录之前，通过 CMake `add_compile_options(-O3)` 同时优化 C 和 C++。
   没有修改模型、量化格式、特征处理、CTC 解码或启用 fast-math。
2. 先前绕过原生构建任务生成的 APK 仍带旧 `.so`；不能用它验证源码中的新优化。
   完整构建后增加三层检查：编译命令的最终优化选项、原生输出与 stripped 输出的 ELF build ID、
   APK 内 `.so` 与 stripped 输出的 SHA256。此外检查两个内置模型的 SHA256 和 C++ 运行库。
   人为将旧 `.so` 放回测试 APK 后，校验脚本确实拒绝该包。
3. 恢复临时字幕的完整句子上下文，移除此前为慢内核添加的 6 秒截尾和忙时跳过策略。
   队列仍合并等待中的临时结果、优先处理最终句子；保留 PCM 转换缓冲复用。
4. 增加 `FunASRPerf` 日志：任务排队、解码、采集丢弃、最终任务丢弃、Java 回调到 `setText`。
   日志不包含识别文字。完整字幕仍在应用私有目录的 TSV/SRT 中。

## 最终任务优先策略

临时任务之间不互相取消。等待中的临时任务仍由 `SegmentQueue` 合并，正在执行的临时任务可以
完成并更新字幕；这样不会因为每秒一次的预览更新而出现“临时字幕永远没有结果”。

当 VAD 产生最终任务时，`final_epoch` 增加。正在运行的临时任务通过 GGML CPU 后端的 abort
callback 检测到 epoch 变化后返回 `GGML_STATUS_ABORTED`，其结果不回调界面；最终任务仍使用完整
句子音频，且不注册取消回调。临时任务已经生成的音频副本不会被删除，环形采集缓冲也不受影响。
因此这条路径最多少一次中间预览，不会减少最终任务的识别音频。日志用 `cancelled=1` 标记此路径。

如果最终任务没有等待，callback 一直返回 false，临时任务按正常流程完成。采集环形缓冲溢出、
VAD 没检测到语音和最终任务队列溢出仍是独立的问题，不能由取消策略修复。

使用新增的真机测试入口主动让一个 11 秒临时推理立即中止，返回耗时约 46 ms 且没有文字；
紧接着执行同一模型的普通推理，仍输出完整英文句子，耗时约 1830 ms。
这验证了 GGML 中止后的后端可以继续执行，属于取消路径回归测试，不代表真实播放中一定会触发取消。

## 同音频、同设备、同线程对比

- 手机：Xiaomi 22041211AC，MT6895Z/TCZA，Android API 34，ARM64。
- 模型：SenseVoice Small Q8 + FSMN-VAD，与 README 的模型哈希一致。
- 测量程序链接的是从相应 APK 解出的原生库，没有另编一套识别算法。
- 下表均为 4 线程。基线每段 1 次，新版每段 3 次，展示新版中位数。
- 固定音频为 16 kHz、单声道 PCM16。独立基准测试时停止字幕服务和视频播放。
- 测量不含模型加载、采集、VAD 分段、字幕显示；RTF = 解码耗时 / 音频时长。

| 音频 | 旧 APK | 新 APK 三次耗时（ms） | 新版中位数 | 新版 RTF |
| --- | ---: | --- | ---: | ---: |
| 6 秒中文 `sample.wav` | 33,030.271 ms | 706.783 / 712.994 / 716.443 | 712.994 ms | 0.119 |
| 11 秒英文 `english-test.wav` | 58,606.555 ms | 1280.243 / 1285.395 / 1307.642 | 1285.395 ms | 0.117 |

这两段输入的解码约快 46 倍；不能据此承诺所有手机、音频和温度条件都有相同比例。
较早的一轮修复后复测中，中英文中位数分别为 909.149 / 1598.921 ms，仍显著快于原基线。
测试没有控制散热和 CPU 频率，因此不把轮次间的细微差异当作代码收益。
最终包的模型加载耗时约 186–187 ms（文件缓存状态未控制，不是首次启动模型复制耗时）。

两段音频的旧版与新版识别文字均相同。英文使用现有参考文本计算 WER：22 个词，
替换 0、删除 0、插入 0，WER 0%。这只是一个短样本的回归检查，不能代表总体英文准确率，
也不能证明中英混合、快语速或噪声场景没有漏词。中文只验证了输出一致，未计算正式 CER。

## 线程与大小核实验

优化内核的 11 秒英文，每个线程配置各测 3 次：

| 线程 | 中位数（ms） | 最小–最大（ms） |
| --- | ---: | --- |
| 2 | 2931.643 | 2899.765–2934.489 |
| 4 | 1598.921 | 1585.079–1677.334 |
| 6 | 1871.922 | 1859.039–1910.855 |
| 8 | 2146.562 | 1830.811–2736.874 |

这台设备目前选用 4 线程，应用原有默认值也是 4；线程更多不保证更快。
之前以不同音频、不同片段长度的屏幕耗时推断“8 线程更快”不成立，由此表替代。

另外在 Bilibili 播放、字幕服务停止时，用同一可执行程序比较系统调度（`taskset ff`）
与四个高性能核心（`taskset f0`）。反向顺序复测的中位数分别为 1938.696 / 1913.010 ms，
约差 1.3%，首轮差异未稳定复现，因此没有加入绑定 CPU 核心的产品代码。

## Bilibili 真实播放

使用安装后的完整 APK，4 线程、系统播放音频采集、透明悬浮窗。
启动会话约 5 分钟，输出时间轴从 21.740 s 到 303.900 s，共 196 次字幕回调、38 个最终句子。
开始时短暂切换过视频，随后主要播放《失业一年，你会失去什么，又会得到什么？【0基础失业指南】》；
这是功能和运行性能验证，不是经过逐字标注的准确率测试。

手机默认关闭了普通应用日志，开启单独的 `log.tag.FunASRPerf=I` 后，
取得 12:49:45.747–12:53:02.660 的 134 次解码与显示记录，其中 23 次为最终句子：

| 指标 | P50 | P95 | 最大值 |
| --- | ---: | ---: | ---: |
| 单次解码 | 1242.09 ms | 2713.81 ms | 3836.17 ms |
| 任务排队 | 315.44 ms | 1100.19 ms | 2460.55 ms |
| 入队到解码完成 | 1510.26 ms | 3775.67 ms | 5483.43 ms |
| 回调到调用 `setText` | 11.691 ms | 19.290 ms | 23.525 ms |
| 单次解码 RTF | 0.237 | 0.340 | 0.749 |

采用 nearest-rank 分位数。该日志区间内，采集环形缓冲丢弃计数和最终句子队列丢弃计数均为 0；
两次中途截图及末段日志确认悬浮字幕持续变化，没有重现“播放约 30 秒后停止输出”。
计数为 0 只说明这两个缓冲没有丢弃，不能排除 VAD 没检测到语音或模型识别错误。

**上述耗时不是声音到屏幕显示的端到端延迟。** 入队发生在 VAD 分段之后，
不包含采集、VAD 等待；`setText` 时间也不是屏幕实际呈现时间。
当前临时结果至少积累约 1 秒音频，长句每次仍需重新识别完整上下文，
最终结果还要等待断句。后续降低长句延迟，应优先评估可取消的过期临时推理和增量计算，
并使用固定播放材料同步录屏/音频测量端到端指标。

运行中一次内存快照为 PSS 328,509 KiB、RSS 464,284 KiB、Swap PSS 18,663 KiB。
电池温度快照由 36.9°C 到 38.4°C；设备接着 USB，不能据此计算耗电率或判定长期温升。
测试结束后已停止字幕服务和视频播放。30 分钟稳定性、第二台设备及完整中英混合 WER/CER 仍待验收。

## 复现与产物身份

完整构建（包含主机分段测试、Android lint、APK、原生库与模型校验）：

```powershell
pwsh -File scripts/build.ps1 -Configuration Debug
```

Gradle 的 Java unit test 任务目前显示 `NO-SOURCE`，不能当作已经执行了 Java 单元测试。
实际执行并通过的是主机 C++ 分段/队列测试，另有 lint 和真机运行验证。

手机开启 USB 调试，停止其他识别与播放负载后，运行独立基准（音频需自行提供）：

```powershell
pwsh -File scripts/benchmark-device.ps1 -AudioPath D:\code\funasr\english-test.wav -Threads 4 -Repeats 3
# 多线程扫描，在 PowerShell 内用数组传参：
& ./scripts/benchmark-device.ps1 -AudioPath D:\code\funasr\english-test.wav -Threads @(2,4,6,8) -Repeats 3
```

多设备连接时加 `-Serial`。可用 `-ApkPath` 指定要测的兼容 APK。
脚本解出实际原生库，编译小型测试入口，记录 APK / 库 / 音频哈希，并将日志保存到 `build/perf/<label>/`。
它不会停止其他应用，也不会推送或发布代码。

真实播放时采集统计（`adb` 位于本项目 `.android-sdk/platform-tools/`）：

```powershell
adb shell setprop log.tag.FunASRPerf I
# 启动字幕并播放视频后，取得本轮进程 ID；不要混入多个会话。
adb shell pidof com.wso4133560.funasrsubtitle
adb logcat -d --pid=<本轮进程ID> -v threadtime -s FunASRPerf:I '*:S' > build/perf/live.txt
pwsh -File scripts/summarize-perf.ps1 -LogPath build/perf/live.txt -OutputPath build/perf/live.json
```
